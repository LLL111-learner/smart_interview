## 一、索引原理（B+树）

### 为什么使用B+树？
| 数据结构 | 问题 |
|----------|------|
| 二叉搜索树 | 可能退化为链表，O(n) |
| AVL/红黑树 | 树高较大，磁盘IO次数多 |
| B树 | 非叶子节点也存数据，每个节点能放的key较少 |
| Hash | 不支持范围查询、不支持排序 |
| **B+树** | 多路平衡，矮胖结构，减少IO；叶子节点形成有序链表，支持范围查询 |

### B+树特点
- 非叶子节点只存索引（键值），不存数据，能容纳更多key
- 所有数据都存储在叶子节点
- 叶子节点通过双向链表连接，支持范围查询和排序
- 树高一般2-4层，千万级数据通常3层即可

### 索引类型
- **聚簇索引（主键索引）**：叶子节点存储完整行数据，一张表只能有一个
- **二级索引（辅助索引）**：叶子节点存储主键值，查询需要回表
- **覆盖索引**：查询的字段都在索引中，无需回表
- **联合索引**：多个字段组成的索引，遵循最左前缀原则

### 最左前缀原则
联合索引 (a, b, c)：
- 可以使用索引：`WHERE a=1`、`WHERE a=1 AND b=2`、`WHERE a=1 AND b=2 AND c=3`
- 不能使用索引：`WHERE b=2`、`WHERE c=3`、`WHERE b=2 AND c=3`
- 部分使用：`WHERE a=1 AND c=3`（只用到a）

### 索引失效场景
1. 对索引列使用函数或运算：`WHERE YEAR(create_time)=2024`
2. 隐式类型转换：字符串字段不加引号 `WHERE name=123`
3. LIKE左模糊：`WHERE name LIKE '%abc'`
4. OR条件中有非索引列
5. 使用 != 或 NOT IN（可能失效，优化器决定）
6. 联合索引不满足最左前缀

## 二、事务ACID与隔离级别

### ACID特性
| 特性 | 说明 | 实现机制 |
|------|------|----------|
| 原子性(Atomicity) | 事务要么全部成功，要么全部回滚 | undo log |
| 一致性(Consistency) | 事务前后数据保持一致 | 其他三个特性保证 |
| 隔离性(Isolation) | 并发事务互不干扰 | MVCC + 锁 |
| 持久性(Durability) | 提交后数据持久保存 | redo log |

### 隔离级别
| 隔离级别 | 脏读 | 不可重复读 | 幻读 |
|----------|------|-----------|------|
| READ UNCOMMITTED | 可能 | 可能 | 可能 |
| READ COMMITTED | 不可能 | 可能 | 可能 |
| REPEATABLE READ(默认) | 不可能 | 不可能 | 可能(MVCC大部分解决) |
| SERIALIZABLE | 不可能 | 不可能 | 不可能 |

### 并发问题
- **脏读**：读到其他事务未提交的数据
- **不可重复读**：同一事务中两次读取同一数据结果不同（数据被修改）
- **幻读**：同一事务中两次范围查询结果行数不同（数据被插入/删除）

## 三、MVCC原理

### 核心概念
MVCC（Multi-Version Concurrency Control，多版本并发控制）通过保存数据的多个版本来实现并发读写不冲突。

### 实现机制
**隐藏字段**：每行记录包含：
- `DB_TRX_ID`：最后修改该行的事务ID
- `DB_ROLL_PTR`：回滚指针，指向undo log中的上一个版本

**undo log版本链**：
- 每次修改都会在undo log中保存旧版本
- 通过回滚指针串成版本链

**Read View（读视图）**：
- `m_ids`：生成Read View时活跃的事务ID列表
- `min_trx_id`：活跃事务中最小的ID
- `max_trx_id`：下一个要分配的事务ID
- `creator_trx_id`：创建该Read View的事务ID

**可见性判断**：
1. 若数据的trx_id == creator_trx_id → 可见（自己修改的）
2. 若数据的trx_id < min_trx_id → 可见（事务已提交）
3. 若数据的trx_id >= max_trx_id → 不可见（事务在Read View之后创建）
4. 若数据的trx_id在m_ids中 → 不可见（事务还未提交）
5. 若数据的trx_id不在m_ids中且 < max_trx_id → 可见

### RC与RR的区别
- **RC（READ COMMITTED）**：每次SELECT都生成新的Read View
- **RR（REPEATABLE READ）**：事务中第一次SELECT生成Read View，后续复用

## 四、SQL优化策略

### EXPLAIN分析
关键字段：
| 字段 | 重点关注 |
|------|----------|
| type | 访问类型：system > const > eq_ref > ref > range > index > ALL |
| key | 实际使用的索引 |
| rows | 预估扫描行数 |
| Extra | Using index(覆盖索引)、Using filesort(文件排序)、Using temporary(临时表) |

### 优化策略
1. **合理建索引**：高频查询字段、WHERE/ORDER BY/GROUP BY字段、区分度高的字段
2. **避免SELECT ***：只查询需要的字段，利用覆盖索引
3. **分页优化**：深分页使用游标或延迟关联
   ```sql
   -- 优化前
   SELECT * FROM orders LIMIT 1000000, 10;
   -- 优化后（延迟关联）
   SELECT * FROM orders o
   INNER JOIN (SELECT id FROM orders LIMIT 1000000, 10) t ON o.id = t.id;
   ```
4. **避免大事务**：减少锁持有时间
5. **批量操作**：INSERT批量插入、UPDATE分批执行
6. **JOIN优化**：小表驱动大表、被驱动表的关联字段加索引
7. **子查询改JOIN**：子查询可能创建临时表，效率较低

## 五、分库分表

### 拆分策略
- **垂直拆分**：按业务模块拆分（用户库、订单库、商品库）
- **水平拆分**：按数据行拆分（按用户ID哈希、按时间范围）

### 分片键选择原则
1. 数据分布均匀
2. 查询最频繁的字段
3. 避免跨分片查询
4. 常用：用户ID、订单ID

### 分布式ID方案
| 方案 | 优点 | 缺点 |
|------|------|------|
| UUID | 简单 | 无序，影响B+树性能 |
| 数据库自增 | 有序 | 性能瓶颈 |
| Redis自增 | 高性能 | 依赖Redis |
| 雪花算法(Snowflake) | 有序、高性能、不依赖外部 | 时钟回拨问题 |

### 常见中间件
- **ShardingSphere**：Apache顶级项目，支持Sharding-JDBC（客户端分片）和Sharding-Proxy（代理模式）
- **MyCat**：数据库代理中间件

### 分库分表带来的问题
1. 跨分片查询
2. 分布式事务
3. 全局排序/分页
4. 数据迁移和扩容

## 六、数据类型与使用场景

### 五种基本类型
| 类型 | 底层结构 | 典型场景 |
|------|----------|----------|
| String | SDS（简单动态字符串） | 缓存、计数器、分布式锁、Session |

## 七、持久化机制

### RDB（Redis Database）
- **原理**：定时将内存数据以快照形式写入磁盘（dump.rdb）
- **触发方式**：
  - 配置规则自动触发：`save 900 1`（900秒内有1次修改）
  - 手动触发：`BGSAVE`（fork子进程，不阻塞）、`SAVE`（阻塞主进程）
- **优点**：文件小、恢复速度快
- **缺点**：可能丢失最后一次快照后的数据

### AOF（Append Only File）
- **原理**：将每个写命令追加到AOF文件
- **同步策略**：
  - `always`：每个命令都同步，最安全但最慢
  - `everysec`：每秒同步一次（推荐，最多丢1秒数据）
  - `no`：操作系统决定，性能最好但不安全
- **AOF重写**：定期重写AOF文件，压缩体积（`BGREWRITEAOF`）
- **优点**：数据丢失少
- **缺点**：文件大、恢复速度慢

### 混合持久化（Redis 4.0+）
- AOF重写时，先写RDB格式数据，再追加增量AOF命令
- 兼具RDB的快速恢复和AOF的数据安全

## 八、缓存穿透/击穿/雪崩

### 缓存穿透
**定义**：查询一个一定不存在的数据，缓存和数据库都查不到，每次请求都打到数据库。

**解决方案**：
1. **布隆过滤器**：在缓存前加一层布隆过滤器，过滤掉一定不存在的key
2. **缓存空值**：查询为空也缓存结果（设置较短过期时间）
3. **参数校验**：接口层做参数合法性校验

### 缓存击穿
**定义**：某个热点key过期的瞬间，大量并发请求同时打到数据库。

**解决方案**：
1. **互斥锁**：只允许一个请求查数据库并回写缓存，其他请求等待
2. **逻辑过期**：不设置TTL，在value中存过期时间，过期后异步更新
3. **热点数据永不过期**：对热点key不设置过期时间

### 缓存雪崩
**定义**：大量key同时过期或Redis宕机，请求全部打到数据库。

**解决方案**：
1. **随机过期时间**：在基础过期时间上加随机值，避免同时过期
2. **Redis集群**：主从+哨兵或Redis Cluster，避免单点故障
3. **多级缓存**：本地缓存(Caffeine) + Redis + 数据库
4. **限流降级**：通过Sentinel等组件限流保护数据库

## 九、分布式锁

### 基于Redis的分布式锁实现

#### 基本实现
```
SET lock_key unique_value NX EX 30
```
- NX：key不存在时才设置（互斥）
- EX：设置过期时间（防死锁）
- unique_value：唯一标识（防误删）

#### 释放锁（Lua脚本保证原子性）
```lua
if redis.call("get", KEYS[1]) == ARGV[1] then
    return redis.call("del", KEYS[1])
else
    return 0
end
```

### Redisson实现
- **看门狗机制（Watchdog）**：自动续期，默认锁30秒，每10秒续期一次
- **可重入锁**：内部使用Hash结构记录加锁次数
- **公平锁/读写锁**：提供更丰富的锁类型

### RedLock算法
- 在N个独立Redis节点上加锁（N>=5，通常5个）
- 大多数节点（N/2+1）加锁成功且总耗时小于锁过期时间，才算加锁成功
- 争议：Martin Kleppmann认为RedLock不够安全（NPC问题：Network delay、Process pause、Clock drift）

### Redis分布式锁 vs ZooKeeper分布式锁
| 维度 | Redis | ZooKeeper |
|------|-------|-----------|
| 性能 | 高 | 相对较低 |
| 可靠性 | AP，可能短暂不一致 | CP，强一致性 |
| 实现复杂度 | 简单 | 相对复杂 |
| 适用场景 | 高并发、允许极端情况下少量不一致 | 对一致性要求高 |
