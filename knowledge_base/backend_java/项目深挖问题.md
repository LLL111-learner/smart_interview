# Java后端项目深挖问题库

---

## 一、项目概览类

### 1. 请简单介绍一下你的项目，你在其中负责什么？
**追问方向**：
- 项目的业务背景和目标用户是什么？
- 团队有多少人？你的角色定位？
- 你负责的模块具体包括哪些功能？
- 项目的整体架构是怎样的？

**评价标准**：
- 优秀：清晰描述项目背景、技术栈、个人职责，突出自己的核心贡献
- 良好：能说清项目和个人职责，但缺乏技术深度
- 一般：描述模糊，无法区分个人贡献和团队工作
- 较差：对自己负责的部分都说不清楚

### 2. 你的项目使用了什么技术栈？为什么选择这些技术？
**追问方向**：
- 对比过其他技术方案吗？
- 这个技术选型是谁做的决定？基于什么考虑？
- 在使用过程中遇到了什么问题？
- 如果重新选择，你会做出什么改变？

**评价标准**：
- 优秀：理解技术选型背后的原因，能对比分析不同方案的优劣
- 良好：能说出技术栈，但对选型原因理解一般
- 一般：只能罗列技术名称
- 较差：对使用的技术了解很浅

---

## 二、技术挑战类

### 3. 你在项目中遇到的最大技术挑战是什么？是如何解决的？
**追问方向**：
- 当时有哪些可选方案？为什么选择了最终方案？
- 解决过程中走了哪些弯路？
- 从这次经历中学到了什么？
- 最终效果如何？有数据支撑吗？

**评价标准**：
- 优秀：问题有深度，解决思路清晰，有量化结果，体现成长
- 良好：能描述问题和解决方案，但缺乏深度思考
- 一般：问题较简单，解决方法常规
- 较差：编造痕迹明显或无法描述解决过程

### 4. 项目中有没有做过性能优化？具体优化了什么？效果如何？
**追问方向**：
- 优化前的性能指标是什么？（QPS、响应时间、内存使用）
- 如何定位性能瓶颈？用了什么工具？
- 优化的具体措施有哪些？
- 优化后的效果提升了多少？

**评价标准**：
- 优秀：有完整的定位-分析-优化-验证闭环，数据清晰
- 良好：有优化经验，但缺乏量化数据
- 一般：只做过简单优化（加索引、加缓存）
- 较差：没有性能优化意识

### 5. 项目中遇到过线上故障吗？是如何排查和处理的？
**追问方向**：
- 当时是怎么发现问题的？监控报警还是用户反馈？
- 排查的思路是什么？用了哪些工具？
- 根本原因是什么？
- 后续采取了什么预防措施？

**评价标准**：
- 优秀：有系统的排查思路，善用工具，有事后复盘和预防措施
- 良好：能定位问题，但排查效率和深度一般
- 一般：解决过简单问题
- 较差：缺乏线上问题处理能力

## 三、系统设计类

### 6. 项目的并发量/数据量有多大？系统如何应对？
**追问方向**：
- 日活用户、QPS峰值分别是多少？
- 数据库数据量级是多少？
- 做了哪些高并发方案？（缓存、消息队列、分库分表）
- 压测过吗？压测指标是什么？

**评价标准**：
- 优秀：对系统容量有清晰认知，有针对性的技术方案
- 良好：能说出大致数据，但缺乏系统性思考
- 一般：数据量较小，未涉及高并发场景
- 较差：对系统的并发量毫无概念

### 7. 如何保证系统的高可用性？
**追问方向**：
- 服务层面做了什么？（集群、负载均衡、熔断降级）
- 数据层面做了什么？（主从复制、读写分离、备份）
- 有没有做过故障演练？
- SLA指标是多少？

**评价标准**：
- 优秀：有完整的高可用方案，涵盖多个层面
- 良好：了解基本的高可用手段
- 一般：只知道概念，缺乏实践
- 较差：对高可用没有认知

### 8. 项目中的接口是如何设计的？RESTful规范？版本管理？
**追问方向**：
- 接口文档如何管理？（Swagger/YApi）
- 统一响应格式是怎样的？
- 接口安全如何保证？（认证、授权、限流）
- 接口幂等性如何处理？

**评价标准**：
- 优秀：有规范的接口设计，考虑了安全性、幂等性等多维度
- 良好：遵循基本RESTful规范
- 一般：接口设计随意，缺乏规范
- 较差：没有接口设计意识

## 四、架构与中间件类

### 9. 项目中是如何使用缓存的？缓存策略是什么？
**追问方向**：
- 缓存了哪些数据？为什么选择缓存这些？
- 缓存的更新策略是什么？（Cache Aside / Write Through / Write Behind）
- 如何保证缓存和数据库的一致性？
- 遇到过缓存相关的问题吗？

**评价标准**：
- 优秀：有完整的缓存设计方案，理解一致性问题
- 良好：使用了缓存，理解基本策略
- 一般：简单使用Redis做缓存
- 较差：不理解缓存的设计考虑

### 10. 项目中使用消息队列了吗？解决了什么问题？
**追问方向**：
- 为什么选择这个MQ？（Kafka/RabbitMQ/RocketMQ）
- 如何保证消息不丢失？
- 如何处理消息重复消费？（幂等性）
- 消息积压怎么处理？

**评价标准**：
- 优秀：深入理解MQ的使用场景，解决过实际问题
- 良好：使用过MQ，了解基本概念
- 一般：仅在简单场景使用
- 较差：不了解MQ

### 11. 项目的数据库设计是怎样的？有没有做过优化？
**追问方向**：
- 表结构设计的原则？范式化还是反范式化？
- 索引是如何设计的？
- 有没有慢查询？怎么优化的？
- 数据量增长后有什么应对方案？

**评价标准**：
- 优秀：数据库设计合理，有优化经验和数据量增长预案
- 良好：基本的表设计和索引使用
- 一般：设计随意，缺乏优化意识
- 较差：不了解数据库设计原则

## 五、协作与流程类

### 12. 项目是如何进行代码管理和协作的？
**追问方向**：
- Git分支策略是什么？（GitFlow / GitHub Flow）
- Code Review流程？
- CI/CD是怎么做的？
- 开发环境、测试环境、生产环境如何管理？

**评价标准**：
- 优秀：有规范的工程化流程，理解DevOps实践
- 良好：使用Git协作，有基本的开发流程
- 一般：只会基本的Git操作
- 较差：缺乏团队协作经验

### 13. 项目中是如何进行测试的？
**追问方向**：
- 单元测试覆盖率是多少？
- 用了什么测试框架？（JUnit、Mockito）
- 有没有做集成测试？压力测试？
- 测试用例是谁写的？

**评价标准**：
- 优秀：有系统的测试策略，单测覆盖率高
- 良好：编写过单元测试
- 一般：依赖手工测试
- 较差：缺乏测试意识

## 六、方案选型类

### 14. 为什么选择这个技术方案而不是其他方案？
**追问方向**：
- 做过哪些技术调研？
- 对比了哪些备选方案？各自的优缺点？
- 做过POC验证吗？
- 有没有考虑过方案的扩展性和维护成本？

**评价标准**：
- 优秀：有系统的调研对比，考虑多维度因素
- 良好：有基本的方案对比
- 一般：直接使用熟悉的技术，缺乏调研
- 较差：不了解其他方案

### 15. 如果让你重新设计这个项目，你会做出哪些改变？
**追问方向**：
- 架构层面有什么改进？
- 技术选型有什么变化？
- 有哪些坑可以提前避免？
- 对团队协作流程有什么建议？

**评价标准**：
- 优秀：有深度反思，改进建议具体可行，体现技术成长
- 良好：能指出一些不足，但改进方向不够具体
- 一般：认为项目已经很好，缺乏反思
- 较差：无法回答

## 七、深度追问通用技巧

### 面试官常用的深挖策略
1. **追问细节**："具体是怎么实现的？"
2. **追问数据**："效果提升了多少？有数据吗？"
3. **追问对比**："为什么不用XXX方案？"
4. **追问异常**："如果出了问题怎么办？"
5. **追问扩展**："如果数据量增长10倍怎么应对？"

### 候选人准备建议
1. 对项目的每个技术点准备至少3层深度的回答
2. 关键数据记清楚：并发量、数据量、性能指标
3. 准备2-3个有深度的技术难点和解决过程
4. 对使用的每个中间件/框架要理解原理，不只是"用过"
5. 诚实面对不会的问题，展示学习思路比胡编更好

---

> **使用说明**：本题库覆盖项目深挖的各个维度，面试模拟时可根据候选人描述的项目特点选择相关问题进行追问。评价标准帮助AI面试官给出客观公正的评分。
