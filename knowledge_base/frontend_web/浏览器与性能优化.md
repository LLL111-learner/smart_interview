# 浏览器原理与性能优化

---

## 一、浏览器渲染流程

### 完整渲染管线
```
HTML → DOM树
              → 渲染树(Render Tree) → 布局(Layout) → 绘制(Paint) → 合成(Composite) → 显示
CSS  → CSSOM树
```

### 详细步骤
1. **解析HTML**：构建DOM树（Document Object Model）
2. **解析CSS**：构建CSSOM树（CSS Object Model）
3. **合并**：DOM + CSSOM → 渲染树（不包含display:none的元素）
4. **布局（Layout/Reflow）**：计算每个节点的精确位置和大小
5. **绘制（Paint）**：将渲染树的节点转化为屏幕上的像素
6. **合成（Composite）**：将不同层合成为最终的屏幕图像（GPU加速）

### 关键渲染路径优化
- CSS放在head中，尽早加载（CSS会阻塞渲染）
- JS放在body末尾或使用async/defer（JS会阻塞HTML解析）
  - `async`：异步加载，加载完立即执行（执行顺序不确定）
  - `defer`：异步加载，DOM解析完后按顺序执行

## 二、重绘与回流

### 回流（Reflow / Layout）
**触发条件**：元素的几何属性发生变化
- 添加/删除DOM元素
- 元素尺寸变化（width、height、padding、margin、border）
- 元素位置变化
- 浏览器窗口大小变化（resize）
- 获取某些属性：offsetWidth、scrollTop、getComputedStyle()（浏览器会强制刷新队列）

### 重绘（Repaint）
**触发条件**：元素外观变化但几何属性不变
- color、background-color、visibility、outline等

### 关系
- 回流一定触发重绘，重绘不一定触发回流
- 回流的性能开销远大于重绘

### 优化策略
1. **批量修改DOM**：使用DocumentFragment或一次性修改className
2. **避免逐条修改样式**：使用cssText或class切换
3. **脱离文档流**：对动画元素使用position: absolute/fixed
4. **使用transform替代top/left**：transform不触发回流，走合成层
5. **避免频繁读取布局信息**：缓存offsetWidth等值
6. **使用will-change提示浏览器**：创建独立合成层

## 三、HTTP / HTTPS / HTTP2

### HTTP/1.1
- 持久连接（Keep-Alive），复用TCP连接
- 管线化（Pipelining），但存在队头阻塞（实际很少使用）
- 支持断点续传（Range头）
- 每个域名最多6个TCP连接（浏览器限制）

### HTTPS
- HTTP + TLS/SSL加密
- 加密过程：
  1. 客户端发起请求，发送支持的加密算法列表和随机数1
  2. 服务器返回数字证书（含公钥）和随机数2
  3. 客户端验证证书有效性
  4. 客户端生成随机数3（预主密钥），用公钥加密后发送给服务器
  5. 双方使用三个随机数生成对称密钥，后续使用对称加密通信

### HTTP/2
- **二进制分帧**：将数据分为更小的帧，提升解析效率
- **多路复用**：一个TCP连接上可以并行传输多个请求/响应，解决队头阻塞
- **头部压缩**：HPACK算法压缩请求头，减少冗余
- **服务器推送**：服务器主动推送资源给客户端
- **优先级控制**：可以设置请求优先级

### HTTP/3
- 基于QUIC协议（UDP之上）
- 彻底解决TCP的队头阻塞
- 0-RTT建连
- 连接迁移（网络切换时不断连）

## 四、跨域解决方案

### 同源策略
- 协议、域名、端口三者完全相同才是同源
- 同源策略限制：AJAX请求、DOM操作、Cookie/localStorage读取

### 解决方案

#### 1. CORS（跨域资源共享） — 最主流
**简单请求**（GET/HEAD/POST + 简单头部）：
- 浏览器自动加Origin头
- 服务器返回 `Access-Control-Allow-Origin` 头

**预检请求**（非简单请求）：
- 浏览器先发OPTIONS预检请求
- 服务器返回允许的方法、头部、有效期
- 预检通过后才发送实际请求

```
// 服务器响应头
Access-Control-Allow-Origin: https://example.com
Access-Control-Allow-Methods: GET, POST, PUT
Access-Control-Allow-Headers: Content-Type, Authorization
Access-Control-Allow-Credentials: true  // 允许携带Cookie
Access-Control-Max-Age: 86400           // 预检缓存时间
```

#### 2. 代理服务器
- 开发环境：webpack-dev-server / vite的proxy配置
- 生产环境：Nginx反向代理
```nginx
location /api {
    proxy_pass http://backend-server;
}
```

#### 3. JSONP（仅GET请求）
- 利用`<script>`标签不受同源策略限制的特性
- 动态创建script标签，服务器返回callback包裹的数据
- 安全性差，只支持GET，已不推荐使用

#### 4. 其他方案
- postMessage：跨窗口通信
- WebSocket：不受同源策略限制
- 服务端转发

## 五、首屏优化策略

### 资源加载优化
1. **路由懒加载**：按路由分割代码，首屏只加载必要代码
2. **代码分割（Code Splitting）**：动态import拆分大模块
3. **Tree Shaking**：移除未使用的代码（需要ESM模块化）
4. **资源压缩**：gzip/brotli压缩（Brotli压缩率比gzip高15-20%）
5. **CDN加速**：静态资源部署到CDN节点

### 渲染优化
6. **SSR/SSG**：服务端渲染/静态站点生成，直接返回HTML内容
7. **骨架屏**：加载时显示页面骨架，提升感知性能
8. **预渲染（Prerender）**：构建时生成HTML（适合少量静态页面）

### 网络优化
9. **预连接**：`<link rel="preconnect" href="//cdn.example.com">`
10. **预加载**：`<link rel="preload" href="critical.css" as="style">`
11. **预获取**：`<link rel="prefetch" href="next-page.js">`（空闲时加载下一页资源）
12. **HTTP/2**：多路复用，减少连接建立开销

### 指标衡量
| 指标 | 说明 | 优秀 |
|------|------|------|
| FCP (First Contentful Paint) | 首次有内容绘制 | < 1.8s |
| LCP (Largest Contentful Paint) | 最大内容绘制 | < 2.5s |
| FID (First Input Delay) | 首次输入延迟 | < 100ms |
| CLS (Cumulative Layout Shift) | 累积布局偏移 | < 0.1 |
| TTI (Time to Interactive) | 可交互时间 | < 3.8s |

## 六、懒加载与预加载

### 图片懒加载
```html
<!-- 原生懒加载（推荐） -->
<img src="image.jpg" loading="lazy" alt="">

<!-- Intersection Observer API -->
<script>
const observer = new IntersectionObserver((entries) => {
  entries.forEach(entry => {
    if (entry.isIntersecting) {
      const img = entry.target
      img.src = img.dataset.src
      observer.unobserve(img)
    }
  })
})
document.querySelectorAll('img[data-src]').forEach(img => observer.observe(img))
</script>
```

### 组件懒加载
```javascript
// Vue
const AsyncComponent = defineAsyncComponent(() => import('./HeavyComponent.vue'))

// React
const LazyComponent = React.lazy(() => import('./HeavyComponent'))
```

### 预加载
```html
<!-- 关键资源预加载 -->
<link rel="preload" href="font.woff2" as="font" type="font/woff2" crossorigin>
<link rel="preload" href="hero.jpg" as="image">

<!-- 下一页资源预获取 -->
<link rel="prefetch" href="next-page.js">
```

## 七、Webpack / Vite 打包优化

### Webpack优化

**构建速度优化**：
1. **缩小搜索范围**：resolve.alias、resolve.extensions、include/exclude
2. **缓存**：cache配置持久化缓存（Webpack5内置）
3. **多线程**：thread-loader并行处理
4. **DLL预编译**：将不常变化的第三方库预编译

**产出体积优化**：
1. **代码分割**：splitChunks提取公共依赖
2. **Tree Shaking**：mode: 'production'自动开启
3. **压缩**：TerserPlugin压缩JS、CssMinimizerPlugin压缩CSS
4. **图片压缩**：image-webpack-loader
5. **Bundle分析**：webpack-bundle-analyzer可视化分析

```javascript
// splitChunks配置示例
optimization: {
  splitChunks: {
    chunks: 'all',
    cacheGroups: {
      vendor: {
        test: /[\\/]node_modules[\\/]/,
        name: 'vendors',
        chunks: 'all'
      }
    }
  }
}
```

### Vite优势
1. **开发环境**：利用浏览器原生ESM，不需要打包，启动极快
2. **预构建**：使用esbuild（Go编写）预编译node_modules，速度极快
3. **按需编译**：只编译当前页面请求的模块
4. **HMR**：基于ESM的热更新，精准快速
5. **生产构建**：使用Rollup打包，产出体积更小

## 八、图片优化

### 格式选择
| 格式 | 特点 | 适用场景 |
|------|------|----------|
| JPEG | 有损压缩，体积小 | 照片、大图背景 |
| PNG | 无损压缩，支持透明 | 图标、需要透明度的图片 |
| WebP | 比JPEG小25-35%，支持透明和动画 | 主流浏览器（需降级方案） |
| AVIF | 比WebP更小，压缩率更高 | 现代浏览器（兼容性一般） |
| SVG | 矢量图，无损缩放 | 图标、Logo、简单图形 |

### 优化策略
1. **响应式图片**：srcset + sizes 根据屏幕加载不同尺寸
   ```html
   <img srcset="small.jpg 480w, medium.jpg 800w, large.jpg 1200w"
        sizes="(max-width: 600px) 480px, 800px"
        src="medium.jpg" alt="">
   ```
2. **picture标签**：按浏览器能力选择格式
   ```html
   <picture>
     <source srcset="image.avif" type="image/avif">
     <source srcset="image.webp" type="image/webp">
     <img src="image.jpg" alt="">
   </picture>
   ```
3. **懒加载**：loading="lazy"
4. **CDN图片处理**：OSS/CDN提供裁剪、压缩、格式转换参数
5. **CSS Sprite**：小图标合并为雪碧图（现代方案更推荐SVG Sprite或Icon Font）
6. **Base64内联**：小于4KB的图片内联到CSS/HTML中
