# 软件测试核心知识点

---

## 一、测试分类

### 1.1 按测试层级分类
- **单元测试（Unit Testing）**：针对最小可测试单元（函数/方法/类），开发人员编写，要求快速、隔离、可重复。框架：JUnit、TestNG、Pytest、unittest
- **集成测试（Integration Testing）**：验证模块间接口和交互，关注数据传递和调用关系。策略：自顶向下、自底向上、三明治、大爆炸
- **系统测试（System Testing）**：在完整系统环境中验证功能和非功能需求，包括功能测试、性能测试、安全测试、兼容性测试
- **验收测试（Acceptance Testing）**：由用户或客户执行，确认系统满足业务需求。分为α测试（内部用户）和β测试（外部用户）

### 1.2 按测试方法分类
- **黑盒测试**：不了解内部实现，基于需求和规格说明设计用例
- **白盒测试**：基于代码逻辑设计用例，关注代码覆盖率
- **灰盒测试**：了解部分内部结构，常用于接口测试和集成测试

### 1.3 按测试目的分类
- **功能测试**：验证功能是否符合需求规格
- **回归测试**：修改代码后确认未引入新缺陷
- **冒烟测试**：新版本基本功能验证，决定是否进入详细测试
- **探索性测试**：基于测试人员经验和直觉的非脚本化测试
- **性能测试**：负载测试、压力测试、容量测试、稳定性测试
- **安全测试**：渗透测试、漏洞扫描、权限验证
- **兼容性测试**：浏览器、操作系统、设备、分辨率兼容

## 二、用例设计方法

### 2.1 等价类划分法
- **定义**：将输入域划分为若干等价类，每个类中的数据对揭示缺陷具有等价效果
- **分类**：有效等价类（合法输入）和无效等价类（非法输入）
- **原则**：每个等价类至少选取一个代表值作为测试数据
- **示例**：密码长度6-16位 → 有效（8位）、无效短（3位）、无效长（20位）

### 2.2 边界值分析法
- **定义**：在等价类边界及其附近取值设计用例
- **取值规则**：最小值-1、最小值、最小值+1、最大值-1、最大值、最大值+1
- **与等价类的关系**：边界值分析是等价类划分的补充
- **示例**：1-100范围 → 测试0、1、2、99、100、101

### 2.3 判定表法
- **适用场景**：多条件组合，输出依赖条件的不同组合
- **组成**：条件桩、动作桩、条件项、动作项
- **步骤**：列出所有条件和动作 → 填写所有组合 → 合并相同动作的规则 → 生成用例
- **优化**：使用正交表减少组合数量

### 2.4 因果图法
- **定义**：分析输入（因）与输出（果）之间的逻辑关系
- **逻辑关系**：恒等、非、与、或
- **约束关系**：互斥、包含、唯一、要求、屏蔽
- **转化**：因果图 → 判定表 → 测试用例

### 2.5 场景法
- **定义**：模拟用户实际使用场景设计用例
- **基本流**：正常操作路径（Happy Path）
- **备选流**：异常和分支路径
- **适用**：业务流程测试、端到端测试

### 2.6 错误推测法
- **定义**：基于经验和直觉推测可能存在缺陷的地方
- **常见关注点**：空值/null处理、特殊字符、并发操作、边界条件、异常流程

## 三、缺陷管理

### 3.1 缺陷报告要素
- **标题**：简洁准确描述问题现象
- **环境信息**：OS、浏览器、版本号、测试环境
- **重现步骤**：详细的操作步骤（1、2、3编号）
- **预期结果**：根据需求应该出现的行为
- **实际结果**：实际观察到的行为
- **附件**：截图、日志、录屏
- **严重程度**：致命（系统崩溃）、严重（功能不可用）、一般（功能受限）、轻微（UI/文案）
- **优先级**：紧急、高、中、低

### 3.2 缺陷生命周期
```
新建(New) → 指派(Assigned) → 修复中(In Progress) → 已修复(Fixed) → 验证(Verified) → 关闭(Closed)
                                                                         ↓
                                                                    重新打开(Reopened)
         → 驳回(Rejected)  → 关闭(Closed)
         → 延期(Deferred)  → 重新打开(Reopened)
```

### 3.3 缺陷度量指标
- **缺陷密度**：缺陷数 / 代码行数（或功能点数）
- **缺陷发现率**：各阶段发现的缺陷比例
- **缺陷逃逸率**：线上缺陷数 / 总缺陷数
- **缺陷收敛趋势**：新增缺陷和关闭缺陷的时间曲线
- **平均修复时间（MTTR）**：从发现到修复的平均时间
- **缺陷重开率**：修复后又被重新打开的缺陷比例

## 四、Selenium自动化测试

### 4.1 核心组件
- **WebDriver**：浏览器自动化核心API
- **浏览器驱动**：ChromeDriver、GeckoDriver（Firefox）、EdgeDriver
- **通信协议**：W3C WebDriver协议（JSON over HTTP）

### 4.2 元素定位方式（8种）
| 方式 | 方法 | 适用场景 |
|------|------|---------|
| ID | find_element(By.ID, "id") | 首选，唯一性最高 |
| Name | find_element(By.NAME, "name") | 表单元素 |
| Class Name | find_element(By.CLASS_NAME, "cls") | 样式类名 |
| Tag Name | find_element(By.TAG_NAME, "div") | 标签类型 |
| Link Text | find_element(By.LINK_TEXT, "text") | 超链接全文 |
| Partial Link Text | find_element(By.PARTIAL_LINK_TEXT, "part") | 超链接部分文字 |
| CSS Selector | find_element(By.CSS_SELECTOR, "#id .cls") | 灵活强大 |
| XPath | find_element(By.XPATH, "//div[@id='x']") | 最灵活，可定位任意元素 |

### 4.3 等待机制
- **强制等待**：`time.sleep(n)`，不推荐
- **隐式等待**：`driver.implicitly_wait(10)`，全局轮询等待
- **显式等待**：`WebDriverWait(driver, 10).until(EC.visibility_of_element_located(...))`，推荐

### 4.4 常见操作
- 窗口切换：`driver.switch_to.window(handle)`
- iframe切换：`driver.switch_to.frame(element)`
- Alert处理：`driver.switch_to.alert.accept()`
- 下拉框：`Select(element).select_by_value("val")`
- 文件上传：`element.send_keys("/path/to/file")`
- JavaScript执行：`driver.execute_script("js code")`
- 截图：`driver.save_screenshot("path.png")`

## 五、Appium移动端测试

### 5.1 架构原理
- 基于WebDriver协议，C/S架构
- Client（测试脚本）→ Appium Server（Node.js）→ 设备驱动 → 设备/模拟器
- Android使用UIAutomator2驱动，iOS使用XCUITest驱动

### 5.2 Desired Capabilities关键配置
```json
{
  "platformName": "Android",
  "platformVersion": "12",
  "deviceName": "Pixel_5",
  "app": "/path/to/app.apk",
  "automationName": "UiAutomator2",
  "appPackage": "com.example.app",
  "appActivity": ".MainActivity",
  "noReset": true
}
```

### 5.3 移动端特有操作
- **手势操作**：滑动（swipe）、长按（long_press）、多点触控（multi_touch）
- **系统交互**：返回键、Home键、通知栏、权限弹窗处理
- **混合应用**：Native和WebView上下文切换（`driver.switch_to.context("WEBVIEW_xxx")`）
- **设备操作**：安装/卸载应用、截图、录屏、模拟GPS定位

## 六、JMeter性能测试

### 6.1 核心概念
- **线程组（Thread Group）**：模拟并发用户
- **取样器（Sampler）**：HTTP请求、JDBC请求、FTP请求等
- **监听器（Listener）**：聚合报告、查看结果树、响应时间图
- **断言（Assertion）**：响应断言、JSON断言、持续时间断言
- **前置/后置处理器**：参数化、关联提取
- **定时器（Timer）**：固定定时器、随机定时器、恒定吞吐量定时器
- **逻辑控制器**：循环控制器、IF控制器、事务控制器

### 6.2 参数化方式
- **CSV Data Set Config**：从CSV文件读取测试数据
- **用户定义的变量**：固定参数值
- **函数助手**：`${__Random()}`、`${__time()}`、`${__UUID()}`
- **正则表达式提取器/JSON提取器**：从响应中提取动态数据

### 6.3 分布式压测
- Master-Slave架构：一台主控机+多台压力机
- 配置：`jmeter.properties`中配置`remote_hosts`
- 注意事项：压力机之间时间同步、数据文件分发、结果汇总

### 6.4 关键性能指标
- **TPS/QPS**：每秒事务数/查询数
- **响应时间**：Average、Median、P90、P95、P99
- **错误率**：失败请求占比
- **吞吐量（Throughput）**：单位时间处理的请求量
- **并发数**：同时在线的虚拟用户数

## 七、Postman接口测试

### 7.1 核心功能
- **请求构建**：支持GET/POST/PUT/DELETE/PATCH等HTTP方法
- **环境变量**：Global、Environment、Collection、Local四级变量
- **Pre-request Script**：请求前执行的JavaScript脚本（生成签名、设置时间戳等）
- **Tests脚本**：响应后的断言和数据提取

### 7.2 常用断言语法
```javascript
// 状态码断言
pm.test("Status code is 200", function () {
    pm.response.to.have.status(200);
});

// 响应体JSON断言
pm.test("Check user name", function () {
    var jsonData = pm.response.json();
    pm.expect(jsonData.name).to.eql("张三");
});

// 响应时间断言
pm.test("Response time < 500ms", function () {
    pm.expect(pm.response.responseTime).to.be.below(500);
});

// 提取数据到环境变量
var jsonData = pm.response.json();
pm.environment.set("token", jsonData.data.token);
```

### 7.3 自动化运行
- **Collection Runner**：GUI内批量执行Collection中的所有请求
- **Newman**：命令行工具，`newman run collection.json -e env.json -r htmlextra`
- **CI/CD集成**：Jenkins Pipeline中调用Newman，生成HTML报告

## 八、CI/CD中的测试

### 8.1 持续集成测试策略
- **代码提交触发**：每次push执行单元测试和静态分析
- **PR/MR触发**：代码审查前执行完整单元测试+集成测试
- **定时触发**：每日/每周执行全量回归测试和性能测试
- **发布触发**：部署前执行冒烟测试和验收测试

### 8.2 Jenkins Pipeline测试集成
```groovy
pipeline {
    stages {
        stage('Unit Test') {
            steps {
                sh 'mvn test'  // 或 pytest、npm test
            }
            post {
                always {
                    junit 'target/surefire-reports/*.xml'
                }
            }
        }
        stage('Integration Test') {
            steps {
                sh 'mvn verify -Pintegration-test'
            }
        }
        stage('E2E Test') {
            steps {
                sh 'npx playwright test'
            }
            post {
                always {
                    publishHTML(target: [reportDir: 'playwright-report', reportFiles: 'index.html'])
                }
            }
        }
    }
}
```

### 8.3 质量门禁（Quality Gate）
- 单元测试通过率 100%
- 代码覆盖率 ≥ 80%（行覆盖）
- 静态分析无严重/阻断问题（SonarQube）
- 接口测试通过率 100%
- 性能基线不退化（响应时间、错误率）

## 九、测试覆盖率

### 9.1 代码覆盖率类型
- **语句覆盖（Statement Coverage）**：每条语句至少执行一次
- **分支覆盖（Branch Coverage）**：每个判定的真假分支至少执行一次
- **条件覆盖（Condition Coverage）**：每个条件的真假至少取一次
- **路径覆盖（Path Coverage）**：覆盖所有可能的执行路径（通常不切实际）
- **MC/DC覆盖**：每个条件独立影响判定结果（航空等安全关键领域）

### 9.2 覆盖率工具
| 语言 | 工具 | 说明 |
|------|------|------|
| Java | JaCoCo | 字节码插桩，Gradle/Maven集成 |
| Python | Coverage.py | `coverage run -m pytest && coverage report` |
| JavaScript | Istanbul/NYC | `nyc mocha` 或 Jest内置 |
| Go | go test -cover | 标准库自带 |

### 9.3 覆盖率的正确认知
- 高覆盖率不等于高质量（可能缺少有效断言）
- 100%覆盖率不切实际也不经济
- 关注增量覆盖率（新代码的覆盖率）比总覆盖率更有意义
- 覆盖率是手段不是目标，最终目标是发现缺陷和保障质量

## 十、SQL数据库测试

### 10.1 测试场景
- **数据完整性**：必填字段NOT NULL、外键约束、唯一性约束
- **CRUD验证**：增删改查操作后数据库状态正确
- **数据类型**：字段类型、长度、精度是否符合设计
- **默认值**：未传值时默认值是否正确
- **触发器和存储过程**：逻辑正确性
- **并发操作**：事务隔离级别、死锁处理

### 10.2 常用测试SQL
```sql
-- 检查数据一致性
SELECT COUNT(*) FROM orders WHERE user_id NOT IN (SELECT id FROM users);

-- 检查重复数据
SELECT email, COUNT(*) cnt FROM users GROUP BY email HAVING cnt > 1;

-- 检查NULL值
SELECT COUNT(*) FROM products WHERE price IS NULL OR name IS NULL;

-- 检查数据范围
SELECT * FROM orders WHERE amount < 0 OR amount > 999999;

-- 检查关联数据
SELECT o.id FROM orders o
LEFT JOIN order_items oi ON o.id = oi.order_id
WHERE oi.id IS NULL;
```

### 10.3 数据库性能测试关注点
- 慢查询分析：`EXPLAIN` 执行计划分析
- 索引有效性：是否走了预期索引
- 连接池配置：最大连接数、空闲连接回收
- 读写分离：主从延迟对业务的影响
- 分库分表后的查询路由正确性
